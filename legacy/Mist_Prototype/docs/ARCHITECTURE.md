# Архітектура локального прототипу та пілоту

Прототип реалізує концепцію з наданого `к7.pdf`: розділ «Мої документи», електронна черга і дуальна освіта зі структурованими проміжними звітами.

## Поточна реалізація

| Компонент | Відповідальність |
| --- | --- |
| HTML і CSS | Семантична оболонка, діалоги, навігація, адаптивний інтерфейс |
| `core.js` | Чиста функція переходів стану, перевірка передумов, версії, журнал подій |
| `views.js` | Генерація екранів відповідно до демонстраційної ролі |
| `captcha.js` | Google reCAPTCHA v2 (тестовий site key) на вході вкладки; без серверної перевірки |
| `app.js` | Оброблення подій, форм, FileReader, localStorage, чернетки |
| `documents.js` | Перегляд, HTML для друку/PDF та відновлення вкладень |
| localStorage | Запити, справи, звіти, Base64-вкладення та історія на одному origin |
| Каталог сервісів | `leokart`, `dormitory`, `erasmus`: картки без черги, готові зразки `DOC-LEOKART` / `DOC-DORMITORY` / `DOC-ERASMUS` |
| Статичний сервер | `scripts/dev-server.cjs` або `scripts/dev-server.ps1` роздає `dist` на `127.0.0.1:5500` без API |

Основні сутності: Student, Company, DocumentRequest, DualCase, Report, Approval, AuditEvent. Погодження містить автора, час, номер версії та коментар.

Сховище використовує ключі `mist.prototype.v1`, `mist.preferences.v1`, `mist.report-draft.v1`. Скидання видаляє лише дані цього прототипу. CAPTCHA тримає `mist.captcha.v1` у `sessionStorage` і не скидається разом із демо.

## Переходи

| Процес | Послідовність |
| --- | --- |
| Документ | У черзі → Готується → Готово |
| Альтернативи документа | У черзі → Скасовано студентом; У черзі / Готується → Відхилено з причиною |
| Справа | Очікує компанію → Погодження плану → Навчання триває → Навчання завершено |
| Звіт | У наставника → У куратора → Результат підтверджено |
| Доопрацювання | Наставник або куратор повертає → Студент подає нову версію → Повторна перевірка наставником |

Завершення справи вимагає підтвердження всіх трьох результатів, окремого рішення та підтвердження куратора. Перевірки кількості годин не замінюють оцінювання результату.

## Підключення до університету: наступний етап

1. **Вхід із Moodle через LTI 1.3.** Замість перемикача ролей сервер перевіряє підписаний запуск, аудиторію, issuer, nonce та відповідність зареєстрованій платформі; роль куратора додатково звіряється з призначенням на програму/групу.
2. **Доступ компанії.** Університет перевіряє партнерську компанію та призначає наставника. Запрошення обмежене терміном, роллю та конкретними студентами. Підтвердження пошти саме по собі не надає академічних повноважень.
3. **Сервер застосунку.** Виносимо правила з `core.js` у серверну реалізацію. Сервер перевіряє роль і доступ до кожного запису, переходу та файла; додає захист сесій, CSRF, обмеження запитів і конкурентних змін.
4. **База даних.** Студенти, заявки, плани, результати й погодження зберігаються в базі з транзакціями, розділенням доступу за університетом і журналом подій.
5. **Файли.** Замість Base64 у браузері — закрите сховище, контроль доступу, перевірка MIME і вмісту, антивірусна обробка, контроль розміру та строків зберігання.
6. **Авторитетне джерело статусу.** Узгоджений імпорт або API навчального обліку із датою актуальності. Членство в курсі Moodle не замінює підтвердження чинного статусу студента. Недоступні чи застарілі дані переводять заявку на перевірку.
7. **Документи.** Погоджені шаблони, повноваження відповідального працівника, справжній електронний підпис за процедурою закладу, версія та перевірка цілісності документа. Демоверсія цього не виконує.
8. **Результат.** У пілоті — погоджений експорт для відповідального працівника; інтеграція внесення до відомості додається після погодження процедури університетом.
9. **Масштабування.** Черги для документів і сповіщень, кілька екземплярів сервера, ізоляція даних закладів, навантажувальні випробування. Мільйони користувачів не перевірені цим прототипом.

## Доступність

Робота з комп’ютера без обов’язкового смартфона, клавіатурна навігація, видимий фокус, підписані поля, нативні діалоги, короткі форми, збереження текстової чернетки, адаптивне компонування. Повний аудит доступності та сценарії допомоги оператором належать до пілоту.

## Перший пілот

Один факультет із погодженим процесом дуальної освіти, 20–30 студентів і 1–2 компанії. Першим перевіряється прийнятність електронного процесу для деканату та куратора, джерело даних і сумісність налаштувань Moodle. Оцінюємо час оформлення, кількість візитів, повернень і ручних перенесень даних.

Макет Erasmus+ уже є в каталозі сервісів. Зарахування кредитів з PDF Transcript of Records залишено як майбутнє розширення.
